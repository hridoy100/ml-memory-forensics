Can a model be reconstructed from RAM?

A running neural network holds more than its weights in memory. It also needs a hierarchy of objects, layer settings, tensor metadata, and executable model logic. This project tests whether those pieces can be recovered from a Linux memory image and used to reproduce the model's predictions.

I used a custom CIFAR-10 CNN as a known reference. Training ran on Argon; the final capture used CPU inference in an Ubuntu ARM64 VM. GDB identified the live objects, LiME acquired RAM, and a custom Volatility 3 plugin followed the model structures offline. A separate validator compared the recovery with the reference. The reconstructed model then matched every prediction and output logit on the 6,000-image test set.

The model-state and TorchScript results come from the original capture of PID 3183. Later native-code experiments use a separate warm capture. The distinction matters when interpreting coverage.

Step 1

Train a custom CIFAR-10 CNN

The network is defined directly with torch.nn. It uses six 3×3 convolutions, three batch-normalization layers, ReLU, and three pooling stages. A two-layer classifier maps the flattened 128×4×4 features through 256 units to ten class logits. No prebuilt network is used.

I pooled CIFAR-10's original training and test sets, then made a disjoint, stratified split with seed 42. Random crop and horizontal flip apply only to training images.

Step 2

Export the checkpoint to TorchScript

The training checkpoint stores state and split metadata. A separate export loads the weights on CPU, switches the model to evaluation mode, scripts it with torch.jit.script, and saves an archive that LibTorch can load.

Export and prepare held-out images
python export_model.py \
  --checkpoint outputs/best_model.pt \
  --output outputs/cifar10_torchscript.pt
python prepare_test_images.py --checkpoint outputs/best_model.pt

The test binary contains the exact 6,000 held-out images selected by the checkpoint. Each record has one label byte and 3,072 planar RGB bytes. The exporter reloads the saved archive and checks its outputs against the checkpoint-built model.

Step 3

Build C++ inference with debug information

The C++ program loads the scripted archive with torch::jit::load, normalizes pixels using (pixel / 255.0 - 0.5) / 0.5, and evaluates batches of 128. CPU inference keeps the tensor allocations in system RAM.

Ubuntu Debug build
cmake -S cpp -B cpp/build-ubuntu -DCMAKE_BUILD_TYPE=Debug \
  -DCMAKE_PREFIX_PATH="$(python -c 'import torch; print(torch.utils.cmake_prefix_path)')"
cmake --build cpp/build-ubuntu --parallel 1

./cpp/build-ubuntu/cifar10_inference \
  outputs/cifar10_torchscript.pt data/cifar10_test.bin outputs/cpp_predictions.csv

The CMake configuration retains full application debug information with -g3, -O0, frame pointers, and header-type retention flags. Complete C++ types were important: the prebuilt runtime did not supply all the debug types needed for object inspection. The final target was rebuilt natively for ARM64.

Step 4

Stop before the forward pass

The breakpoint is on the application's forward call at line 91 of the preserved main.cpp. At that point the model and normalized input batch are loaded, and the process can remain stopped while another terminal acquires memory.

GDB

Follow the model objects and tensor storage

The model Object pairs ClassType descriptions with IValue slots. Object-valued slots lead to child modules; tensor-valued slots lead to TensorImpl, StorageImpl, and the allocation holding the values. ClassType also holds layer constants and methods.

The target package reported PyTorch 2.14.1+cpu and revision 5c4886908584029761b579af026dcfb627c84070. Field offsets were measured from retained DWARF types and matching headers. The kernel symbol table and PyTorch ABI profile have different roles: one describes Linux, the other the application's C++ structures.

Step 6

Capture RAM and find the process offline

LiME was built for the running Ubuntu kernel. Volatility used the matching kernel symbol table and an experimental ARM64 branch, with two plugin requirements patched to allow AArch64. PsList found PID 3183 and Maps listed 128 VMAs.

Analyze the preserved LiME image
framework_dir="$HOME/Downloads/volatility3-aarch64-experimental"
"$framework_dir/.venv/bin/python" "$framework_dir/vol.py" -q \
  -f "$HOME/Downloads/memory-evidence/ubuntu.lime" linux.pslist.PsList --pid 3183
"$framework_dir/.venv/bin/python" "$framework_dir/vol.py" -q \
  -f "$HOME/Downloads/memory-evidence/ubuntu.lime" linux.proc.Maps --pid 3183

The original module insertion reported “Invalid parameters” but left a LiME-format image. Its header and hash were recorded, and the target pages were analyzed successfully. This supports the target recovery; it does not certify a complete or atomic capture of every system page. The later warm acquisition returned status zero.

Step 7

Verify GDB's addresses with Volshell

Volshell switched to the captured process layer and translated its virtual addresses. The model and input pointers matched the GDB values. The input TensorImpl reported rank four, shape [128, 3, 32, 32], and 393,216 elements.

A GDB virtual address is not an offset into the LiME file. The process layer translates it through the captured page tables. The verifier reads actual pages without padding missing data and ends with ADDRESS_CHECK_PASS.

Step 8

Recover the weights, hierarchy, and implementation

The mlmodel.PytorchModel plugin starts from the captured PID and root Object pointer. It walks named attributes and child modules, checks tensor shape, dtype, strides, storage offset, and allocation bounds, then saves the recovered values. It does not load the training checkpoint or original model definition.

GraphFunction methods and graph SourceRanges lead to resident Source objects. The plugin joins their string-view pieces and saves the generated TorchScript code with hashes and provenance. It also records graph topology and source relationships.

Recovery from the original PID-3183 image
ArtifactRecovered and checked
Weights and buffers22 parameters + 9 batch-normalization buffers; all 31 match in name, shape, dtype, and bytes
Model hierarchy26 module objects; names, types, and registration order match
Function graphs34 materialized graphs with topology/source records
ImplementationAll 19 archived generated TorchScript source files match byte for byte

The replay helper instantiates the captured hierarchy and tensors and compiles the recovered function bodies as Python after annotation/cast erasure. Explicit adapters connect the used intrinsics to Python and the installed CPU runtime. The reference archive is loaded afterward for comparison.

On all 6,000 test images, predictions and output logits matched exactly. Both implementations classified 5,225 images correctly. This tests reconstruction on the held-out set, not every possible input.

What code coverage means here

All 34 reported generated-code functions have recovered definitions. The first batch of the Python replay made 49 calls to 31 distinct recovered functions. The two Sequential __len__ definitions and training-only _verify_batch_size helper were recovered but not exercised.

The static inventory lists 23 runtime dependencies; 12 were called through the replay adapter. Resolving a call to installed PyTorch does not mean that operation's native implementation was recovered. This replay trace is separate from the original C++ process and from the native trace below.

Extension

Recover selected native function bodies

Generated TorchScript source describes the model, but its operators still rely on native runtime code. The original image could not read the selected convolution code range. A separate LiME capture of PID 4540, taken after one completed batch, recovered that function's full 584-byte body.

A later live trace in C++ PID 2782 observed 40 entry hits across ten of twelve candidate symbols. Their bodies were then extracted from the warm PID-4540 image. ELF build identity and file offsets connected the runs despite different process addresses.

All ten ELF-symbol-sized ranges matched the reference library byte for byte. The plugin reads only captured process memory, rejects missing pages, and never fills gaps from the reference file. These are nested function calls, not 40 model layers.

Other functions in the saved stacks—including the graph executor, interpreter, dispatcher, and generated wrappers—were observed but not recovered as complete bodies in this extraction. Internal/indirect callees and backend libraries do not have exhaustive coverage. Body bytes can also include padding or blocks that did not execute.

Results and interpretation

The recovered state, hierarchy, and generated implementation were sufficient to reproduce this model's evaluation outputs on the held-out set. The reference served as a validation target, not as a source for the extractor's weights or code.

Limits

Recovery is guided by a known PID and root Object address and uses a build-specific ABI profile. The demonstrated tensors are contiguous CPU allocations. Replay uses a compatibility layer rather than a newly reconstructed standalone TorchScript archive. GPU VRAM, automatic model discovery, original native C++ source, and exhaustive native call/branch coverage are outside the demonstrated result.

The graphs preserve topology/source relationships but are not a complete IR serializer. Matching outputs establish agreement on these inputs. The broader reading of “any code called during forward” remains partially demonstrated because every native callee has not been inventoried and recovered.

Reproduce the checks

The repository contains the model and C++ code, GDB helpers, both Volatility plugins, the measured ABI profile, tests, and small evidence files. Private model binaries, RAM images, kernel symbols, and recovered tensor/binary files are excluded from Git.

Check the tracked evidence
git clone git@github.com:hridoy100/ml-memory-forensics.git
cd ml-memory-forensics
python3 scripts/verify_evidence.py

This verifies saved evidence hashes and report consistency; it does not repeat extraction or inference. The running instructions give the analysis commands and artifact paths. The full walkthrough keeps the acquisition and inspection steps together.

The final environment used Ubuntu ARM64, kernel 7.0.0-38-generic, PyTorch 2.14.1+cpu, and an experimental Volatility 3 ARM64 revision. The environment and evidence notes record exact revisions, release-date qualifications, and screenshot provenance.
